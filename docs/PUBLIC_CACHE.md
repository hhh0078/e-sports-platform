# 公共静态数据缓存与默认运营内容

文件作用：说明后端公开缓存范围、一天TTL、失效恢复及默认内容幂等规则，避免将鉴权、资金或私密关系误放入公共缓存。

## 缓存范围

服务端Redis数据TTL为86400秒；接口仍使用`Cache-Control: no-store`，客户端和CDN不会继续展示不可撤销的一天旧内容。

| 公开数据 | 缓存部分 | 保留实时部分 |
| --- | --- | --- |
| `/api/games` | 启用游戏目录、主题、素材、分类与稳定排序 | 发布、分享目标和交易资格仍查真实游戏状态 |
| `/api/bootstrap` | 公开站点字段、游戏目录、审核模式摘要 | 不包含AI或支付密钥 |
| `/api/agreements` | 当前公开协议正文 | 登录同意版本仍在原事务中核对 |
| `/api/financial-rules` | 公开费率和最低押金规则 | 订单锁定费率、钱包金额、押金资格和出款继续走原事务 |
| `/api/public-content` | 原始公共运营配置 | 每次解析当前游戏及真实可用跳转，不缓存账号公告已读 |
| `/api/articles` | 仅空搜索词、limit=20、offset为0/20/40/60/80的五个已发布常用页 | 搜索、其它页大小、深页、非对齐偏移及管理查询直接实时读取 |
| `/api/articles/{id}` | 以文章ID和当前正文摘要区分的安全HTML渲染结果 | 当前文章状态、正文来源和图片可见性仍验证 |

服务、俱乐部、玩家主页不整包缓存。它们复用公开财务规则基础块，钱包实缴、认证、成员关系、管理权限、服务可售状态、评价可见性和订单状态继续实时读取。`mine`、`managed`、所有管理详情、鉴权、会话、提现、聊天、公告账号已读均不进该缓存。

最终`publicValue`和图文审核安全投影仍在缓存之后运行。命中不重复读取完整静态业务数据或数据库缓存版本；有审核、可见性及跳转安全检查的接口仍保留必要SQL，不能宣称整个请求完全不访问数据库。

文章列表不按自由搜索参数生成缓存。公共调用者即使不断更换搜索词、页大小或百万级偏移，也不能制造一天有效的海量空结果键；符合准入的空页仍可缓存，列表数据键严格最多五个。超出缓存准入只回源，不改变API筛选、分页、总数或状态码，TTL仍为86400秒。文章详情键只来自实际存在且已发布的文章及数据库正文摘要，任意未知ID和查询参数不会制造详情缓存。

公共缓存与会话等能力共享Redis，不依赖全局LRU淘汰来保护容量，也不修改Redis全局内存策略。代际失效只阻止旧值命中，旧键仍按TTL到期；容量控制因此必须在请求准入时完成。

## 代际、事务与故障恢复

键使用环境隔离前缀`public-read:v1:`，参数只保存摘要。每个值同时保存其`generation`。读取及回填分别通过Lua原子检查就绪租约和代际；保存期间发生失效时，旧请求可以完成当次读取，但不能把旧结果写回当前缓存。

`public_cache_outbox`为仅含序号和时间的持久队列。游戏、文章、固定公开配置和公开图片撤销，通过数据库触发器与源修改同事务登记；包括直接SQL和审核`putRaw`。普通用户、钱包、订单和资金事务不触发该队列。

相关管理接口仅在成功保存后主动投递，鉴权或校验失败不会重置代际，避免匿名失败请求迫使全站回源；若处理器提交后又异常返回，持久队列仍由后台每秒恢复。领取仅锁定队列行，不占用原资金事务；Redis成功之后才提交队列删除。Redis失败或进程中断会保留待投递事实；重复投递只推进新代际，不改变业务数据。队列序号不被当成提交顺序，避免小序号事务晚提交时被遗漏。

正常配置保存返回前已尝试主动失效。进程恰好在源事务提交后中断、或者外部直接改SQL时，后台在下一轮恢复；该途径是最终一致性，不能声称跨PostgreSQL和Redis原子提交。就绪租约为5秒，后台失联后不再命中缓存，当前进程投递或缓存失败立即回源。正常后台每秒查询小型失效队列，不在每个缓存命中请求中查数据库版本。

启动缓存worker时主动更换代际；Redis丢失数据或重新连接会恢复代际与就绪租约。失败响应不缓存。缓存故障不把已成功提交的保存改报失败；交易及账号安全检查始终采用原实时路径。

## 默认运营内容稳定标识

- 文章：`platform-intro-v1`、`newcomer-rules-v1`。
- 平台首图：`platform-intro-v1`，图片`/static/operations/platform-intro-v1.png`。
- 新人公告图片：`/static/operations/newcomer-rules-v1.png`，仅一次展示，公告版本单调增加。
- 迁移标记：`platform-default-content-v1`；原公共配置备份：`platform-default-content-backup-v1`。

只有全新安装自动初始化；已有部署使用显式命令应用。标记成功后重启和再次执行不会覆盖管理员后续编辑。原平台轮播及游戏分组保留，默认首图只插入一次；已有12项且没有默认首图时整笔拒绝，不擅自删除。公告替换前在同事务保存完整原公开配置；空白提示和须知才补默认。文章编号冲突时拒绝覆盖，全部步骤同事务成功或回滚。

内置图片按固定路径和用途白名单开放，不支持任意`/static/`路径、目录或Markdown源码下载；用户上传仍走原裁剪、尺寸、归属和后置审核。

两篇正式正文原稿在`docs/default-content/`，与`backend/internal/assets/operations/`中内嵌副本一致。Docker构建只需要backend上下文，不从服务器工作目录动态加载Markdown。

已有站点先由发布流程创建完整数据库和配置备份，再在新镜像中显式执行：

```sh
docker compose exec -T api /app/jijie-default-content apply --actor-id <已有平台根管理员ID>
```

该命令不启动API、不自动建表、不创建用户或登录会话；操作者在事务内重新核验根管理员权限。成功结果包含`applied`、`already_applied`、`revision`、`backup_id`、`article_ids`及`cache_invalidation_pending`。后者为true表示业务已经提交，后台仍会恢复缓存失效，不能据此重新创建运营内容。重复运行会返回已有版本，不覆盖后续人工修改。

新装默认资料使用系统来源登记正常文本后置审核及审计，不创建系统账号；显式应用则绑定真实操作者。两张内嵌平台素材为受信固定资源，不伪装成用户上传。原公告备份保存在settings的`platform-default-content-backup-v1`；恢复旧展示内容应通过新配置修订进行，不能倒写公告版本和已读历史。

## 验证边界

真实本地PostgreSQL隔离schema及Redis隔离前缀测试覆盖命中、TTL、坏缓存、回滚、乱序提交、旧回填、投递失败恢复、后台恢复、媒体撤销、公开分页及私密接口绕过。生产部署、真实微信支付、真机及真实AI决定必须另行记录；本文件不把本地测试写成线上验收。
