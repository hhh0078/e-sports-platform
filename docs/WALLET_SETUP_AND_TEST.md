# 钱包配置与测试清单

文件作用：说明本轮钱包源码的资金规则、微信支付与商家转账配置、数据库升级边界和逐项测试步骤。本文不包含密钥，不是运行测试通过或已上线的证明。

本轮没有通过服务器MCP重新部署钱包后端。小程序正式包在本地构建，也不等于服务器已具有这些新接口；原2026-10-20生产记录不能作为钱包上线记录。实际构建、自动测试与微信界面结果以本轮验收产物为准。域名、Docker、微信登录及首次管理员配置沿用 [部署指南](DEPLOYMENT.md)。

## 1. 钱包规则与入口

用户入口为“我的 → 我的钱包”，个人资料页及发布服务页也有轻入口。未登录时先登录，再返回钱包。一个账号同时具有玩家与打手能力，平台押金完全自愿，不缴纳也能发布、接单；手机号、账户冻结、服务审核等原校验仍有效。

所有金额由后端按人民币整数分记账，页面仅展示结果：

| 资金区 | 含义 | 可消费 | 可提现 |
| --- | --- | --- | --- |
| 充值余额 `recharge_cents` | 用户实际充值到账的余额 | 可以 | 不可以 |
| 可提现余额 `available_cents` | 通过售后期复核的服务收入 | 可以 | 可以，需审核及微信结果 |
| 待结算 `pending_cents` | 已付款并托管给打手、尚未释放的服务收入 | 不可以 | 不可以 |
| 提现冻结 `withdrawal_frozen_cents` | 已申请提现，等待审核或微信终态的收入 | 不可以 | 不可重复申请 |
| 有效平台押金 `deposit_cents` | 自愿缴纳、尚未申请退还的押金 | 不可以 | 只能申请原路退还 |
| 押金退还中 `deposit_refunding_cents` | 已申请退还、尚未获微信成功确认的部分 | 不可以 | 继续冻结等待原路退款 |

订单支付可选“微信支付”或“钱包余额”。可消费余额仅为充值余额与可提现收入之和，不包含待结算、冻结或押金。余额支付优先使用充值款，再使用服务收入；退款按原支付的两种资金分账精确退回，不把充值款变成可提现收入。

服务完成后保留7天售后期。到期后打开钱包或申请提现，后端重新核对已付款、真实托管、完成时间及售后状态，满足条件才释放收入。退款申请、平台介入、微信退款处理中，以及尚无平台最终裁决的卖家拒绝退款，都不会直接释放。开发测试付款与演示订单不构成真实收入。

### 自愿押金

- 只有后端返回的当前有效押金大于0，服务卡片和详情才显示“平台押金”。详情展示真实金额，并注明“仅展示缴纳金额，不是赔付承诺”。这与俱乐部自行设置的规则押金是两回事。
- 退还申请立即把申请金额从有效押金转入“退还中”。这部分不再计入标识；部分退款后未申请退还的剩余押金仍有效。
- 后端同时检查用户作为老板、打手的真实订单。待付款、未完成、退款/争议处理中不能退；完成订单仍在7天售后期内也不能退。已取消、已退款或已过售后期且无待处理售后的订单才可放行。
- 退还中，相关账号不能新建、支付或认领新订单，防止一边退押金一边产生新交易。待微信确认全部申请退款完成后解除限制。
- 押金按原充值来源分笔原路退回，不转成钱包余额。网络超时、未知结果、`ABNORMAL`、`CLOSED` 不当作成功，也不擅自解冻；点击原申请“同步”，由平台核查实际渠道状态。

### 提现状态

| 状态 | 页面含义 | 资金处理与下一步 |
| --- | --- | --- |
| `pending_review` | 待审核 | 申请金额已冻结；管理员可拒绝或审核发起转账 |
| `processing` | 处理中 | 按原商户单号查询，超时不解冻，不能用拒绝按钮回退 |
| `wait_user_confirm` | 待确认 | 本人在钱包点击“确认收款”，按微信原生提示操作后再同步 |
| `success` | 成功 | 微信已确认成功，冻结额扣除一次 |
| `failed` | 失败 | 微信明确失败或取消，收入解冻一次 |
| `rejected` | 已拒绝 | 管理员拒绝尚未发起的申请，收入解冻一次 |

余额充值及押金不能用于提现。单笔提现2000元及以上，按当前微信接口规则填写本次实名；服务端加密发送，不公开姓名、密文或OpenID。关闭确认收款弹窗、客户端提示成功、等待了一段时间，都不能替代后端查询或已验签通知。

## 2. 微信支付配置

先由运营者准备实际小程序主体、与AppID绑定的微信支付商户、所经营服务对应权限。开通结果和允许的资金用途由微信及实际商户资质决定，保存配置不代表已获批。

管理员点击：**我的 → 平台管理中心 → 微信支付**。

| 页面字段 | 后端字段 | 填写说明 |
| --- | --- | --- |
| 微信支付商户号 | `merchant_id` | 与小程序绑定的实际商户号 |
| 商户API证书序列号 | `certificate_serial` | 对应本商户签名私钥的证书序列号 |
| 微信支付公钥ID | `platform_public_key_id` | 对应验签公钥，不能误填本商户证书序列号 |
| APIv3密钥 | `api_v3_key` | 32字节，仅在后台秘密输入框填写 |
| 商户私钥PEM | `merchant_private_key_pem` | 完整商户私钥，包括起止行 |
| 微信支付平台公钥PEM | `platform_public_key_pem` | 与公钥ID对应的公钥或平台证书 |
| 支付结果通知地址 | `notify_url` | `https://game.ai.58it.cn/api/payments/wechat/notify` |
| 退款结果通知地址 | `refund_notify_url` | `https://game.ai.58it.cn/api/payments/wechat/refund-notify` |

点击“保存支付配置”，核对已配置状态。秘密留空保留原值，已保存内容不会回显。服务器须保留私密 `CONFIG_ENCRYPTION_KEY` 并配合数据库备份，不提交Git或放入源码销售包。AppSecret仍仅在后端配置，不能放到前端。

上述支付通知同时处理订单付款及钱包余额/押金充值；退款通知同时处理订单退款及押金分笔退款，不需要再创造另一套充值回调。更换商户或AppID前，应先核对在途原支付与转账，不能换配置后重建另一笔付款来代替原单查询。

## 3. 商家转账与提现配置

管理员点击：**我的 → 平台管理中心 → 钱包审核**，页面下方为“商家转账配置”。其中“商户密钥与证书沿用支付配置”可打开上一节入口。

| 页面字段 | 后端字段 | 要求 |
| --- | --- | --- |
| 启用真实提现 | `withdrawal_enabled` | 默认关闭，资质和资料完整后由管理员开启 |
| 商家转账场景编号 | `transfer_scene_id` | 使用商户实际获批且适合服务收入的场景，不套用无关现金营销编号 |
| 转账场景报备字段 | `transfer_scene_report_infos` | 按获批场景逐项添加 `info_type`、`info_content`，每项名称1—15字、内容1—32字，最多10项；真实提现至少一项 |
| 转账通知HTTPS地址 | `transfer_notify_url` | `https://game.ai.58it.cn/api/payments/wechat/transfer-notify`，无查询参数 |
| 转账备注 | `transfer_remark` | 真实提现必填，最多32字 |
| 收款感知描述 | `user_recv_perception` | 依获批场景填写，最多10字 |

点击“保存转账配置”。“已就绪”仅表示本项目配置校验通过，实际场景权限和转账是否成功仍由微信决定。不要把微信登录、JSAPI收款开通等同于商家转账权限已开通。

管理员在该页上半部筛选提现申请：待审核申请可点击“审核并发起转账”或“拒绝申请”；处理中、待确认的申请只能点击“同步转账结果”。本人微信确认收款凭据只返回给本人，不出现在管理列表。

三个通知地址均应公网HTTPS可达，沿用已有反向代理；修改自己域名时只替换域名，保留上表精确路径。微信通知不依赖用户会话，而由后端验签、解密及原单校验；不要额外加需要小程序登录的拦截页面。

## 4. 相关接口

页面通过领域API调用，下表供部署和问题定位，不要求运营者手工发送资金请求。`{id}`始终是本人充值/提现/退还申请ID；后台操作只允许平台管理员。

| 用途 | 方法与路径 |
| --- | --- |
| 钱包分区 / 账单 | `GET /api/wallet`、`GET /api/wallet/entries` |
| 充值或缴押金 / 本人记录 | `POST /api/wallet/topups`、`GET /api/wallet/topups` |
| 继续原充值支付 / 同步 | `POST /api/wallet/topups/{id}/pay`、`POST /api/wallet/topups/{id}/sync` |
| 提现申请 / 本人记录 / 同步 | `POST /api/wallet/withdrawals`、`GET /api/wallet/withdrawals`、`POST /api/wallet/withdrawals/{id}/sync` |
| 退押金申请 / 本人记录 / 同步 | `POST /api/wallet/deposit-refunds`、`GET /api/wallet/deposit-refunds`、`POST /api/wallet/deposit-refunds/{id}/sync` |
| 管理提现列表 / 发起或同步 / 拒绝 | `GET /api/admin/wallet/withdrawals`、`POST /api/admin/wallet/withdrawals/{id}/execute`、`POST /api/admin/wallet/withdrawals/{id}/reject` |
| 管理转账配置 | `GET /api/admin/wallet-settings`、`PATCH /api/admin/wallet-settings` |

写资金请求使用稳定 `request_id`，同一账号下绑定唯一用途、原单和金额。响应未知时沿原记录继续支付/同步，不通过更换请求号重复创建同笔业务。

## 5. 本轮数据库迁移与回滚

后端启动时在迁移事务内新增 `wallets`、`wallet_entries`、`wallet_escrows`、`wallet_topups`、`wallet_withdrawals`、`wallet_deposit_refunds`、`wallet_requests`，补充中文注释、唯一索引、非负金额约束和不可变账本触发器。旧用户的接单兼容字段会统一为开启，冻结状态、手机号和角色不变。

升级操作沿用 [部署指南的备份、升级与回滚](DEPLOYMENT.md#10-备份升级与回滚)，但本轮有以下额外要求：

1. **第一次启动新版后端之前**，备份完整PostgreSQL数据库、私密部署配置与支付加密主密钥；保留旧镜像标签，验证备份可恢复。备份不能放公网目录或源码包。本文仅提供操作要求，没有执行生产备份或迁移。
2. 先在独立测试库验证迁移与恢复，再部署生产。开发测试资金库不能改 `DEV_MODE=false` 后当真实库使用；生产启动会检查开发充值、模拟托管及模拟转账记录并拒绝运行。
3. 历史订单没有真实钱包托管或 `wallet_accounted` 标记时，不会自动把旧“收入统计”记入可提现余额。历史真实付款、退款和已线下结算须先与商户账单逐单核对，另行设计受控迁移；不能只把标记改成true或按旧统计补余额。
4. 新版已有真实充值、提现或退款后，旧版镜像不了解这些账本，不能只降级镜像继续经营。先停止新增资金操作、核对在途微信原单，保留最新库；在确认无新增交易的范围内才可恢复匹配的代码与备份。不要直接用升级前备份覆盖已有真实资金记录。
5. 不删除账本触发器、不直接改余额来“修复”未知状态，不执行 `docker compose down -v`。外部资金已变动时，必须以真实商户结果和追加核账证据处理。

## 6. 可逐条执行的测试

每项记录身份、金额、原申请/订单ID、结果与截图；不要记录密钥、OpenID或微信确认凭据。测试产生的订单和资金记录应保留在对应独立环境。

### A. 本地模拟资金

使用本地体验包、明确 `dev_mode=true` 的后端和五种体验身份。8090/18091及客户端编译地址须一致，准备方法见 [微信模拟器复测](WECHAT_SETUP.md#复现微信模拟器-ui-验收当前命令)。以下不发生真实扣款或到账。

- [ ] 访客能看到钱包空结构；点击充值、提现或缴押金需登录，不显示他人余额。我的与个人资料的钱包入口都能正确返回。
- [ ] 所有账号默认具有接单能力，没有账户级开关；未缴押金仍可通过原手机号/资料校验发布与接单。
- [ ] 分别充值余额和缴纳押金；重复点击、关闭后重开或同步同一原记录只入账一次。账单能区分用途，押金不增加可消费/可提现金额。
- [ ] 仅有充值款时申请提现被拒绝；钱包余额付款先扣充值款，余额不足不能付款，押金及待结算不参与支付。
- [ ] 用充值款加服务收入混合支付一单，再取消或完成售后退款，原两种余额精确还原；打手待结算相应撤回，没有额外可提现款。
- [ ] 下单、接单、开始、交付、验收后，打手先看到待结算，未满7天不能提现。满期及争议边界由隔离集成测试夹具检查，不为测试去改真实订单时间。
- [ ] 正押金服务卡在图下有独立标识，详情展示实际金额及非赔付说明；0/未知无标识。发布提醒注明自愿，不影响提交。
- [ ] 分别以老板和打手制造待付款、未完成、退款或介入中的订单，退押金均被拒绝；已完成但仍在7天售后期也不能退。
- [ ] 使用无上述订单的账号，测试多笔押金充值后部分退还和全部退还；申请部分立即不再计有效押金，成功后按原渠道分笔扣减，不能变成余额。
- [ ] 在受控超时测试中保留退还中金额；新建、支付、认领订单被阻止；沿原申请同步完成后解除限制，重复同步不重复退款。
- [ ] 申请提现后可提现减少、冻结增加；管理员拒绝待审申请只解冻一次；模拟成功只扣冻结一次；模拟失败只解冻一次。
- [ ] 普通用户不能访问钱包管理；无关用户不能继续支付、同步或读取他人的私密资金记录；账号切换后旧响应不能回填或继续提交。

### B. 真实微信、商户与真机

仅在钱包后端实际部署、真实商户配置及获批场景齐备后进行。正式包连接HTTPS，生产 `DEV_MODE=false`，启用微信合法域名校验。使用真实普通账号与允许的最低金额；演示服务/订单不能用于资金验收。

- [ ] 使用当前AppID真人登录并主动同意协议，完成真实手机号授权；冻结或未验证账号不能绕过原交易门槛。
- [ ] 核对三类通知精确路径及证书；小程序后端、支付商户及转账场景的AppID/商户绑定一致，配置页面不回显秘密。
- [ ] 真实余额充值与自愿押金分别测试：取消微信付款不增加余额；付款成功后以后端通知/查询为准；客户端断网后从原记录继续或同步，不新建第二笔。
- [ ] 真实余额支付和退款验证原资金分区；微信支付意图已创建时，不允许同单再扣余额；恢复或取消须处理原付款。
- [ ] 以已核验的真实可提现收入申请提现；管理员审核发起，待本人确认时在手机完成原生“确认收款”，同步后与微信实际到账逐笔一致。
- [ ] 关闭收款弹窗、网络切断或转账结果未知时，状态保持处理中/待确认且金额冻结；明确失败或拒绝才解冻，不以客户端提示代替结果。
- [ ] 真实押金部分及全部原路退款，核对每笔原付款渠道实际到账；未知/异常持续冻结，重复通知或同步不重复退钱。
- [ ] 手机移动网络检查付款返回、后台切换、收款确认、图片与聊天；核对玩家、打手、俱乐部管理员、平台管理员和无关账号的权限边界。
- [ ] 最终按商户账单、原订单、托管、钱包分区、不可变流水进行一次完整对账，再决定开放真实用户。

本轮独立 [后端代码审查摘要](../output/game-ui-wallet/backend-review.md) 只代表源码与测试覆盖复核，不替代本地集成测试执行、商户资质、真人确认或真实资金验收。
