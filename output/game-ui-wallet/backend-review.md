# 钱包后端只读复核

文件作用：记录2026-10-22对本轮钱包源代码及已有测试代码的独立复核。审查期间未修改backend、未运行后端测试、未连接生产数据库或真实微信渠道；不能把本文件当作运行测试通过报告。

## 结论与范围

这组改动把充值余额、服务托管收入、提现和自愿押金分区记账，并接入微信原单支付、转账及退款结果。按当前已读取路径，未确认需要修复的资金错账、跨账号操作或秘密公开缺陷。后续提交若继续改动这些路径，需要重新核对。

审查按多个用户可同时充值、接单、付款、申请退押金和提现的场景进行；只检查本项目的事务与接口边界，没有评估商户业务资质或用模拟响应证明真实渠道可用。

## 已追踪的边界

| 边界 | 代码依据与核对结果 |
| --- | --- |
| 不可变账本与重复入账 | `wallet_core.go` 的 `appendWalletEntry` 以用户/业务类型/原业务号生成唯一ID，首次插入才变更余额，重复但载荷不同返回409；`wallet_migration.go` 用UPDATE/DELETE触发器禁止覆盖账单 |
| 同账号资金用途隔离 | 充值、可提现收入、待结算、提现冻结、有效押金、退押金中各自非负；余额付款保存充值款/收入分账，退款精确恢复原来源 |
| 资金请求重放 | `claimWalletRequest` 把同账号request_id绑定用途和规范载荷，不能换金额或跨原单使用；充值、提现与退押金的稳定原单号支持未知响应补偿 |
| 一致锁序 | `lockWalletUsers` 排序取得用户事务锁，`lockWalletOrder` 再锁订单并核对归属快照；订单创建、公开需求创建、付款、认领及退押金走同一用户锁域 |
| 退押金与新交易 | `guardDepositOrders` 同时核对买卖角色、待付款/未完成及售后；申请先移有效押金到退还中，`guardDepositRefunding` 阻止新建、付款、认领抢入 |
| 七天服务收入 | `walletIncomeEligible` 要求真实已付托管、已完成、满七天且没有待处理售后；未最终裁决的拒绝退款也阻止释放；`releaseWalletIncome` 在同锁域每单只释放一次 |
| 充值原单身份 | `applyWXPayment` / `applyWalletTopup` 核对商户、AppID、原单、金额、OpenID、支付流水与币种，已退款充值迟到通知不重新增加押金 |
| 押金原路退款 | `processDepositRefund` 固定分笔原退款号，超时先查原单；`applyDepositRefund` 核对原充值用户、用途、交易流水及总额/分笔额，未知或异常不减冻结额 |
| 提现审核和未知结果 | `finishWalletWithdrawal` 验证原商户单、收款人、金额和微信流水；仅已核验SUCCESS或明确FAIL/CANCELLED终态扣除/解冻，冲突终态拒绝，未知不被管理员拒绝按钮强制解冻 |
| 微信确认参数与公开响应 | `withdrawalResponse` 只向本人待确认状态返回确认包；`publicValue` 清除OpenID、实名密文/哈希、原支付流水及转账配置；管理列表不含本人确认包 |
| 历史与环境 | `wallet_accounted` 为false的历史订单不折算收入；`guardProductionWalletData` 拒绝开发充值/模拟托管/模拟转账数据接入真实支付环境 |

具体读取范围：`wallet_core.go`、`wallet_escrow.go`、`wallet_migration.go`、`wallet_topups.go`、`wallet_deposit_refunds.go`、`wallet_withdrawals.go`、`wallet_settings.go`、`wallet_routes.go`，以及关联的 `orders.go`、`transitions.go`、`admin.go`、`wechatpay.go`、`wechatpay_notify.go`、`server.go`、`store.go` 和业务模型。

## 已检查的测试覆盖及缺口

已阅读 `wallet_test.go` 与 `wallet_payments_test.go` 的验证、混合余额退款、七天及最终售后结算、并发提现防超提、多笔退押金、开发资金拒入生产、支付通知重放/篡改、押金退款超时补偿、提现未知状态与冲突终态、本人确认包隔离、生产余额退款和支付渠道意图冲突场景。这是对测试代码的检查，没有在本次复核中执行这些测试。

复核时尚未看到以下独立回归场景，已通知root与后端实现代理：

1. 用并发屏障直接对撞“退押金”与新建订单/公开需求/付款/认领，证明不能双成功且不死锁。目前已读押金测试主要用顺序请求检查409。
2. 对撞售后期收入释放与退款/提现，核对同一笔托管只能释放或撤回一次，账本总额守恒。
3. 直接验证同账本业务号但不同金额/分区delta的冲突回滚，以及DELETE不可变触发器；现有测试包含UPDATE拒绝、同通知重放与不同支付流水拒绝。

以上是测试保护的缺口，不是已证实的生产漏洞。若后续已补测试，以最终源码及运行结果为准。真实微信商家转账场景审批、真人确认收款、实际充值/退款到账、物理手机网络及通知可达性均未由本次代码复核验证。

代码审查结论：未发现必须修复项。正式资金上线结论须依据最终自动/界面测试、真实商户资格和真实渠道验收独立作出。
